pxf:s3 30여개 external 파티션 테이블을 union all 하여 뷰로 만들어 한번에 조회 시 문제

Greenplum Architectural 특성과 PXF Engine의 한계로 인해 총 1달 기준 1.35TB(parquet 파일 사이즈 기준 평균 45GB × 30개) 용량의 External Table을 단순 UNION ALL로 묶어 조회하면 실행이 실패하거나 무한 대기(Hang) 상태에 빠지기 매우 쉽습니다.

주요 문제점 

	- Java Process 메모리 폭주 : PXF는 Greenplum Segment Node마다 Java 기반 세션(JVM)을 띄워 S3 데이터를 읽고 Parquet을 Deserialization
	30개 외부에 연결된 S3 경로를 병렬로 스캔하면 JVM Heap Memory가 고갈되거나 Garbage Collection(GC) 지연으로 성능이 급격하게 지연
  - 세그먼트 메모리 사용량을 고려하여 JVM 할당 크기 조정 필요, ex) Xmx32g -Xms32g
	- 메모리를 충분히 할당 하더라도 PXF 내부 파라미터를 통한 Connection / Thread Pool 튜닝 필요
	- Query Plan Slice 30개 발생
	- 1.35TB 전체 데이터를 Network 비용 발생
	- Snappy 압축 해제 및 Deserialization 비용도 기본적으로 발생
	- 세그먼트와 S3스토리지 간 네트워크 10Gbps(초당 약 1.25GB) 대역폭을 100% 온전히 활용할 수 있다면, 1.35TB pure network read 자체만으로 약 18분
	- 25Gbps 기준 (초당 약 3.2GB) = 약 7.2분 

#추가 테스트 필요1 

-- 개별 30개 대신 S3 버킷/폴더 하위 전체를 바라보는 1개의 External Table 생성이 되는지 확인 필요
CREATE EXTERNAL TABLE ext_part_tbl_202601 (
    col1 text,
    col2 int,
    ...
)
LOCATION ('pxf://s3-bucket/path/to/part_tbl/part_tbl_202601*/*?PROFILE=s3:parquet')
  FORMAT 'TEXT' (delimiter=E',');

#테스트 필요2

-- 컬럼 Pruning 효과 확인, 필요한 컬럼만 조회 (parquet 에서 특정 컬럼에 대한 값만 전송)하여 전송 속도 향상이 있는지 확인 

CREATE VIEW v_ext_part_tbl_202601 as select * from part_tbl_202601 union all select * from part_tbl_202602 union all select * from part_tbl_202603;

select a,b,c
from v_ext_part_tbl_202601 
where END_DT >= '2026-01-01' AND END_DT <= '2026-01-31'
